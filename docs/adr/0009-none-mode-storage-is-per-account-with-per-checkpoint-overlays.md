# `stateMode:'none'` storage is per-account with per-checkpoint OVERLAYS, and the flat `storageStack` is gone

`SimpleStateManager` keeps storage in ONE flat `Map` keyed `` `${address}_${slot}` ``, and `checkpointSync()` pushes a full COPY of it. `@ethereumjs/evm` checkpoints once per MESSAGE FRAME, so every transaction paid `frames + 1` copies of ALL of state, and `clearStorage(address)` — which the EVM calls on every contract creation — could only be a prefix scan of the whole map. Measured: four ordinary transactions cost 289 ms at 100,000 slots and 10 ms on a layout that copies nothing per frame, and through the node's own public surface ONE transaction at 10,000 slots already ate between a third and nine tenths of the 16.6 ms frame budget. So `stateMode:'none'` storage is now `Map<address, Map<slot, value>>` and a checkpoint pushes an **overlay** — one checkpoint's worth of CHANGE (the slots written since it, plus a tombstone set of the accounts cleared in it) — instead of copying anything. A commit merges the top overlay down and pops it; a revert just pops it; a read walks the stack until it finds the slot or an overlay that cleared the account.

Measured after it shipped, against the layout it replaced: checkpoint 0.31-0.45 µs at every state size (against 71-122 µs at 1,000 slots and 20,000-23,000 µs at 100,000), `clearStorage` ~0.53 µs at every state size (against 15,600-17,500 µs at 100,000), and the four transactions **flat in state size** at ~12 ms whether state holds 1,000 slots or 100,000 — 18x to 28x at 100,000 across two runs. Through the node's public surface at 100,000 slots, a transaction went from 39-94 ms to 2.4-3.0 ms and an `eth_call` from 49.6 ms to ~0.33 ms. Read the FLATNESS rather than any single ratio: the 100,000-slot cell is the allocation-heaviest and moves tens of percent between runs, which is why both runs are transcribed. The full tables, and the re-runnable script, are in `docs/spikes/re-layer-storage-as-per-account-maps-with-per-frame-diffs/measurements.md`; the design and the four candidate layouts it was chosen from are in `docs/spikes/spike-storage-layout-cost-for-the-revm-write-half/measurements.md`.

## One word: overlay

The spike called the same idea an overlay, a diff frame and a journal frame in different places, and its two prototypes named the field `overlays` and `diffs`. The term is **overlay**, in the code, the tests, the commits and `CONTEXT.md`'s glossary. "Frame" was not available: it already means an EVM message frame, and in `CONTEXT.md` it also means the 16.6 ms frame budget. "Journal" was not available either: `@ethereumjs/evm` keeps a journal ABOVE the state manager, and revm keeps one inside wasm, so a third journal one layer down would read as the same object. A future reader meeting three names for one concept will assume they are three concepts.

## This is not the copy-on-write layout ADR 0005 sketched

ADR 0005 anticipated `Map<account, Map<slot, value>>` with copy-on-write checkpoints. That fixes `clearStorage` but leaves the checkpoint O(accounts-with-storage), which is the SAME O(total) when state is one slot per account — exactly the shape per-player game state tends towards (13.8 ms at 100,000 sparse slots in one run of the spike's probe, 85.5 ms in another, because 100,000 live `Map` objects are GC-bound). Adding the overlay removes that term too, and it is a SMALLER change than the copy-on-write ownership bookkeeping it replaces. The naive version — a per-account layout whose checkpoint shallow-copies the outer map and shares the inner ones — is the one to watch out for: a child frame's write then mutates its parent's map, survives a revert, and lands in committed state with no error anywhere. It is kept as a CONTROL in `test/helpers/storage-overlay.ts` and fails 4 of the 6 checkpoint semantics the shipped layout passes.

## The blast radius was NINE sites and three of them answered WRONG

ADR 0005 said the layout could change "behind that one accessor, and only the accessor changes". That clause is **measurably false and is superseded by this ADR** (the correction note on ADR 0005's `clearStorage` section is what defers to this one). With a per-account layout underneath and no other change, the shipped `assertStackShape` still PASSED, `SimpleStateManagerStore.getStorage` answered "this slot is zero" for a slot holding `0x2a` with no throw, and `dumpState`'s `'none'` branch dumped NO storage at all — which persistence would then have saved. The failure mode is wrong answers, not a crash.

Two consequences are therefore load-bearing and must not be undone:

- **The flat `storageStack` is not maintained, and READING it throws.** It was tempting to leave it present and empty, which is what the spike's prototypes did; that is precisely what let three readers answer plausibly and wrongly. A getter that throws, naming `storageAt()` / `liveStorage()`, converts every un-migrated reader from a believable zero into a loud error. That is the honest-edge convention applied to an internal representation.
- **The guard must constrain the REPRESENTATION, not its shell.** `assertStackShape` ("three non-empty arrays of Maps") is replaced by `assertStateShape`, which additionally requires the two storage accessors and the overlay stack's own shape. `test/storage-overlay.spec.ts` feeds it a flat `SimpleStateManager` to prove it refuses one, because a guard that has never refused anything is not known to guard.

## The serialised format did NOT move with the layout

`dumpState` / `loadState` output is persisted data (IndexedDB, `loadState` fixtures) with existing state behind it, so it stays `{address: {slot: value}}` in `0x`-hex and the internal layout moves under it. `test/storage-overlay.spec.ts` asserts the dump byte-identical — including key ORDER — against `test/fixtures/dumpstate-flat-layout.json`, a dump captured from the pre-overlay build, and asserts that same fixture loads back into a node running the new one.

## Consequences

- **`clearStorage` is O(that account)** — in fact O(1) — so ADR 0007's "Cost" section no longer applies, and revm's `StateStore` contract (which requires the same) can be met without translating between two models when the write half arrives.
- **The read half got faster for free.** `eth_call` checkpoints the state manager twice, so it paid the copy too: 49.6 ms to 0.32 ms at 100,000 slots. This was never a revm problem and swapping the interpreter could not have touched it, because the copying was in the state manager.
- **A read now walks the overlay stack**, two map lookups per open checkpoint instead of one. Measured against frame depths 1/2/4/8 it is not distinguishable from the flat map's single lookup, but it is a real term and it is the thing to watch if a contract nests dozens of frames deep.
- **The node is pinned harder to its own state manager.** `revm-state-store.ts` and `dumpState` read `OverlayStorageStateManager`, not `SimpleStateManager`, so a consumer supplying their own state manager (not currently possible through `NodeOptions`) is further away, and the revm engine refuses anything that is not it. That is the same trade ADR 0005 already made, made louder.
- **`shallowCopy()` quietly stopped matching upstream's depth semantics**, recorded here because it was an unasked-for change to a published class's behaviour and nothing else says so. Upstream's `SimpleStateManager.shallowCopy()` PUSHES each stack level onto a freshly constructed manager, whose constructor has already pushed one frame of its own, so upstream's copy ends up ONE FRAME DEEPER than the original. The override here ASSIGNS the stacks instead, so a copy has exactly the original's depth. That is the behaviour a copy should have, and it is why it was not written the upstream way; it is also a deviation a reader would otherwise have to diff two packages to notice. Nothing in this repo calls `stateManager.shallowCopy()` today (the `shallowCopy()` members in `node.ts` and the conformance helper belong to the mock BLOCKCHAIN, not the state manager), so the change is currently unobservable, and it is written down now precisely because that is when it is cheap.
- **Upstream should hear about it**, and it does not block us: any `@ethereumjs/evm` consumer using `SimpleStateManager` pays O(state) per message frame. The fix still has to ship in code WE publish, for ADR 0007's reason (a library consumer resolves `@ethereumjs/statemanager` themselves, so a `pnpm patch` would fix only our own test runs), and more so here, because our own `dumpState` and revm store read this representation directly and upstream has no reason to keep our accessors stable.
- **The packed storage-key encoding is NOT part of this.** Owning the representation was its precondition and is now met, but it is a READ-path change with a different blast radius, so it is deferred to `work/tasks/backlog/revm-state-store-packed-storage-keys.md` rather than mixed in.
