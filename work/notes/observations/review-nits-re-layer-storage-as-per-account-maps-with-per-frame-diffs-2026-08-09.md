## Non-blocking review findings

The PR/code review gate (Gate 2) APPROVED 're-layer-storage-as-per-account-maps-with-per-frame-diffs' but raised the
following non-blocking findings (nits). They do not block integration; this
is their durable home for triage — promote-to-task / keep / delete.

- Ratify the in-scope decisions this build made on its own. No '## Decisions' block was written (commit body is empty, the done record is moved unchanged), but four are recorded durably in ADR 0009 / module JSDoc / the changeset: (1) the inherited flat storageStack is retired and READING it now throws a new loud error (the setter silently swallows writes); (2) the internal rename SimpleStateManagerWithClearStorage -> OverlayStorageStateManager and assertStackShape -> assertStateShape, shipped as a patch bump on the argument that neither is re-exported from index.ts; (3) the revm engine now REFUSES any state manager that is not the node's own (a new refusal at connect time); (4) the core-bundle baseline was re-pinned 413.7 -> 416.3 KB raw / 124.6 -> 125.4 KB gzip, i.e. the default-entry size gate was moved by this change. Each looks right to me; they need a human yes.
  (src/state-manager.ts:150-166 (throwing accessor), src/revm-state-store.ts:117-163 (assertStateShape), docs/adr/0009-*.md, .changeset/per-account-storage-overlays.md, packages/benchmarks/test/evm.spec.ts:129)
- shallowCopy() quietly changes upstream's semantics and this is not recorded anywhere. Upstream SimpleStateManager.shallowCopy PUSHES each stack level onto a freshly constructed manager, so the copy ends up one frame DEEPER than the original (the constructor's own frame sits underneath). The override ASSIGNS instead, so the copy has exactly the original's depth. That is arguably the correct fix, but it is an unasked-for behaviour change on a published class. Nothing in this repo calls stateManager.shallowCopy today (only VM.shallowCopy and EVM.shallowCopy do, and the node uses neither), so impact is currently nil. Ratify or note it in ADR 0009.
  (src/state-manager.ts:364-377 vs @ethereumjs/statemanager 10.1.2 simpleStateManager.js shallowCopy())
- The bottom overlay's cleared set is never pruned. commit() does below.cleared.add(address) unconditionally, but when below is the BOTTOM overlay there is nothing underneath for the tombstone to hide, so every address ever cleared (i.e. every CREATE the node has executed) accumulates a permanent string in overlays[0].cleared. It stays correct, but it is monotonic memory growth in a long-lived browser node and it adds an O(addresses-ever-cleared) term to liveStorage() and therefore to dumpState. Worth a comment at minimum, or skip the tombstone when below is the bottom.
  (src/state-manager.ts commit(): for (const address of top.cleared) { below.written.delete(address); below.cleared.add(address); } and liveStorage() iterating overlay.cleared)
- The dumpState byte-identity claim rests entirely on the provenance of test/fixtures/dumpstate-flat-layout.json, which was added in THIS commit and so cannot be verified from the repo. Its README says it was captured from the pre-overlay build and must not be regenerated; if it had in fact been produced by the new code, dumpStateByteIdenticalToFlatLayout would pass vacuously and the strongest persisted-data guarantee in the change would be unproven. Content is plausible (slot order is global-insertion shaped, and the CREATE / cheat cases are present), so this is a provenance attestation to confirm rather than a suspected defect.
  (packages/embedded-eth-node/test/fixtures/README.md and test/helpers/storage-overlay.ts section 5)
- work/specs/ready/revm-engine-behind-runtx.md is untouched and its RE-SCOPED banner still sends the next tasker to ADR 0005 and src/revm-state-store.ts, describing state access as the THREE public checkpoint stacks. That description is now superseded (two stacks plus storageAt/liveStorage), and story 8's 'measurably faster than today' baseline moved by 17-37x with this change. The spec does carry a not-maintained snapshot banner, and the new measurements doc names story 8, so this is drift-by-design rather than a lie, but adding an ADR 0009 pointer to the spec's banner would stop a future tasker planning against the old mechanism.
  (work/specs/ready/revm-engine-behind-runtx.md frontmatter banner and line 46; docs/spikes/re-layer-*/measurements.md node-surface table)
- The benchmark comment quotes a bare 28x twice, which is the single figure ADR 0009 and the measurements doc explicitly tell readers not to quote (the two runs were 28.2x and 17.9x; the changeset correctly says 18-28x). Align the evm.spec.ts wording with the 18-28x-and-flat claim so the repo does not carry two different numbers for the same measurement.
  (packages/benchmarks/test/evm.spec.ts:96 and :105 vs .changeset/per-account-storage-overlays.md headline)
