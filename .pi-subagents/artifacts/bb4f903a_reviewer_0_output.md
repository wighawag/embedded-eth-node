**Where it breaks.** Two blocking findings, both destination-check / satisfiability rather than bookkeeping:

1. The spec's own Solution sentence names "*and the `evm_*As` trusted variants*" as executing on the installed engine. No task delivers or verifies that. The mechanism is `node.ts:549-553`, which shadows `getSenderAddress()` on an `@ethereumjs/tx` **instance** — a trick that survives only because `runTx` reads the sender through that one call. Whether it survives a neutral seam is an unstated design choice, and getting it wrong executes the transaction as a *different* address with a plausible receipt. `test/helpers/trusted-sender.ts:100` never installs an engine, and the conformance battery only uses `eth_sendRawTransactionSync`, so nothing in the set would catch it. A consumer combining `senderMode:'trusted'` (the repo's advertised fast path) with revm gets silently wrong state.
2. `every-node-feature-survives-a-revm-write-engine.md` requires the existing suites to pass "with a revm engine installed, **UNEDITED**", and the prompt says flatly "AN EDIT TO THOSE SUITES IS A FAILURE SIGNAL". But `test/helpers/persistence-reload.ts:70,137` and `genesis-cheats-perf.ts:41,96,166,211` call `createNode()` with no engine parameter at all, and the revm precedent (`revm-conformance.spec.ts`) needed both an engine-factory parameter *and* its own `cut-revm.ts` bundle. The criterion is literally unsatisfiable, and the task materially understates its own scope.
