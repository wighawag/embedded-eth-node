# The engine is an INJECTED OBJECT, not a named string

> **Amended 2026-08-10** (`re-widen-the-engine-seam-to-cover-transactions`): the decision below is UNCHANGED — an engine is still an injected object and never a name — but the seam's SCOPE widened from reads to reads AND transactions, so `ReadEngine` is now `Engine`, `node.readEngine` is now `node.engine`, and the second and fourth consequences below are superseded. See [the amendment](#amendment-the-seam-covers-transactions-too-so-the-type-is-engine-and-the-property-is-nodeengine).

`createNode()` takes an EVM engine as an OBJECT implementing the `ReadEngine` type (`createNode({engine: await createRevmEngine({wasm})})`), never as a name the core resolves (`createNode({engine: 'revm'})`). The string form is the more obvious API and it is the one we rejected: a name only means something if the core can turn it into code, so the core would have to `import` every engine it can name. That import is unconditional in the module graph, so a bundler cannot tree-shake it away, and a JS-only consumer — the DEFAULT consumer, who never asks for revm — would ship a wasm engine they never call. Story 3 of `work/specs/tasked/revm-engine-behind-eth-call.md` is precisely "I pay nothing for a feature I do not use", so a string option would defeat the feature's own premise. An injected object inverts that: the core references only the interface, the consumer's own import decides what is in their bundle, and an engine the core has never heard of works exactly as well as one we shipped.

This is recorded because it is public API shape (hard to reverse once consumers pass `engine:`), and because the alternative is what a reader would expect to find.

## Consequences

- **The engine is CONSTRUCTED by the consumer, and its context comes from the node.** An injected object exists before the node does, so it cannot capture the node's state manager at construction. The seam therefore has exactly one lifecycle hook, `connect(context)`, called once during `createNode()` with `{stateManager, common, stateMode}`. It is also the honest place for an engine to REFUSE a configuration it cannot serve (ADR 0005: the revm read path has no synchronous view of `MerkleStateManager`, so `stateMode:'trie'` must throw), because a throw there fails node construction rather than the first opcode.
- **`node.readEngine`, not `node.engine`.** Only the READ path (`eth_call`, `eth_estimateGas`, `eth_fillTransaction`'s estimation) is routed through the engine; transactions run on `@ethereumjs/vm` regardless. A node with an injected engine therefore runs TWO EVMs, and an unqualified `node.engine` would let a bug report attribute a receipt to an engine that never touched it. The property carries its scope in its name and reports identity only (`{id}`), so it survives the comlink Worker boundary as a plain value. *(Superseded by the amendment: the property is `node.engine`, and the identity-only `{id}` half stands.)*
- **Purity is the ENGINE's business, not the node's.** The node's pure-read helper no longer checkpoints or resets EIP-2929 warmth; the default `@ethereumjs/evm` engine does both, because both are requirements of THAT EVM. Per ADR 0005, `SimpleStateManager.checkpointSync()` copies all three state maps and clones every account (0.384 ms per call at 2002 accounts, larger than the entire revm read it would wrap), so an engine that structurally cannot commit must not pay for it.
- **The interface stays the smallest thing that serves a read**: return data, execution gas, and whether it failed. Transactions are deliberately NOT designed for here — `work/specs/ready/revm-engine-behind-runtx.md` owns that shape, and guessing it now would get it wrong. Anything a future engine needs and this context lacks (block hashes, for instance) is an additive field on `ReadEngineContext`. *(Discharged by the amendment: that spec came, and the transaction shape was designed then rather than guessed here. The additive-widening rule stands, on `EngineContext`.)*

## Amendment: the seam covers TRANSACTIONS too, so the type is `Engine` and the property is `node.engine`

2026-08-10. `work/specs/tasked/revm-engine-behind-runtx.md` moved transaction execution onto the seam, which is the condition the original text (and `CONTEXT.md`'s glossary) named for widening the word *engine*. The seam is now ONE interface with TWO operations — `call` (read-only) and `transact` (executes and commits) — the default `@ethereumjs/evm` engine implements both, and the node's mining path executes through it rather than calling `runTx` itself. **Nothing about the injected-object decision changed**; what changed is what an engine is asked to do.

**Why one interface rather than a second one.** The read and write paths differ in a transaction's VALIDITY rules, not in their engine-ness: a read relaxes them (base fee, block gas limit, EIP-3607) and cannot commit, a transaction relaxes nothing. That asymmetry belongs to the two OPERATIONS, and stating it in one place where both are visible beats splitting it across two interfaces that could then be pointed at two different EVMs — two identifiers that can disagree, for no gain. There were no third-party engines to break.

**The name broke rather than being aliased.** `ReadEngine` → `Engine`, `ReadEngineContext` → `EngineContext`, `ReadEngineInfo` → `EngineInfo`, `node.readEngine` → `node.engine`, with no deprecation alias, across roughly 150 occurrences in about thirty files inside this repo. A shim would have left two words for one concept from the day it landed, and there is nothing outside this repo depending on the old one. `CHANGELOG.md` is NOT rewritten: it records what shipped under the name that shipped.

**What the seam gained, and it is the point of the change: a neutral transaction result.** `TransactionResult` carries what a RECEIPT needs from an EVM and nothing else — status, gas used (net of refunds), effective gas price, logs in emission order, the logs bloom, any created address — in raw bytes and bigints rather than `@ethereumjs/*` classes. `runTx`'s `amountSpent`, `gasRefund`, `minerValue`, `accessList` and `execResult` are deliberately absent: no receipt reads them, and a field that exists because one engine returns it is what makes two engines incomparable. The effective gas price is now the ENGINE's answer (the node's legacy-safe computation moved behind the default engine) because the engine that executed the transaction is the engine that charged it.

**What did NOT move, on any engine**: block construction, `cumulativeGasUsed`, receipt assembly, the RPC layer, transaction parsing and sender recovery. And `@ethereumjs/vm`'s two `skip*Validation` flags stayed INSIDE the default engine rather than becoming neutral request fields — they are one EVM's vocabulary, and worse, `revm-wasm` REFUSES to combine its equivalent relaxation with committing, so a neutral field would have been a promise the next engine could only throw at. The reasoning is recorded at that code site (`src/engine.ts`).

**`transact` is OPTIONAL, and that is transitional rather than a design.** An engine that omits it leaves the node's transactions on the node's own `@ethereumjs/vm`, which is exactly what every non-default engine did before this change — which is why it is what preserves behaviour. The shipped `embedded-eth-node/revm` engine is in that state until its write half lands, so requiring the method would have meant refusing every transaction on a revm-backed node. A `transact` that is PRESENT but not a function is refused at construction, alongside the existing refusals, because a half-built engine silently mining on `@ethereumjs/vm` is the same class of lie as the fallback this ADR's other consequence exists to prevent.

**`node.engine` reports the engine that was INSTALLED**, still identity-only (`{id}`), still a plain value across the comlink boundary. On a node whose engine implements only the read half, a receipt therefore cannot be attributed to that id — the pre-existing two-EVM shape, now stated in `CONTEXT.md` and the README rather than encoded in a property name.
